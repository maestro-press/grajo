# CLAUDE.md

Index for working on this repo. Load-bearing rules inline; deep reference is in `docs/`.

## Working with this repo

- **Always commit with a positional path arg**: `git commit <path> -m "..."`, not `git add <path> && git commit -m "..."`. Parallel Claude sessions modify the working tree concurrently; `git add` then a bare `git commit` will sweep in unrelated WIP. Verify with `git show --stat HEAD` after every commit. (See `~/.claude/CLAUDE.md` Learnings 2026-04-14.)
- **Always `git pull --rebase` before pushing a branch** — parallel sessions commonly push to `main` between your fetch and your push.
- **Tests** (Node 24 — the one declared version: CI, `engines`, installer and prod units; `tests/node-standard.test.js` keeps them in step): `npm test` runs the FULL suite in a scratch env (safe on any box — it can never touch the real `~/.crow`; see `scripts/run-suite.mjs`). Node built-in test runner, no third-party framework. Single file: `npm test -- tests/<file>.test.js` (or raw `node --test tests/<file>.test.js` — but NOT from a systemd-launched shell without the scratch env). Also verify a server starts cleanly: `node servers/<name>/index.js` (ctrl-C to exit) or `node servers/gateway/index.js --no-auth` for the gateway.
- **CI red blocks ALL merges — including the operator's** (decision Q6, 2026-07-18). The `Tests` workflow (`.github/workflows/test.yml`) runs the full suite + `check-ports` + `build-registry --check` + `npm audit` (critical/prod tier) on every PR and push to main, with no path filters — every commit gets check-runs now; an empty check-runs result on a current sha means something is WRONG, not normal. Query `https://api.github.com/repos/<owner>/<repo>/commits/<sha>/check-runs` (public, no auth) and confirm every run is `completed`/`success` before merging (the legacy commit-status API omits Actions and can read green when a check is red). Job keys `suite`/`static-checks`/`audit` are branch-protection contexts — never add a `name:` to those jobs or rename a key without updating protection. **CI green does NOT cover schema migrations** — `SCHEMA_GENERATION` bumps still require the manual migration rail (`scripts/schema-migration-dryrun.sh`). Notably **any new bundle host port must be added to `docs/developers/port-allocation.md`** or `check-ports` (`scripts/check-port-allocation.js`) fails. (See `~/.claude/CLAUDE.md` Learnings 2026-06-28.)

- **Bundle code changes need a `manifest.json` version bump.** The Extensions page installs a bundle by copying it to `~/.crow/bundles/<id>/`, and `repairInstalledBundleAssets` refreshes that copy ONLY when the repo manifest version differs from the installed one (`refreshVersionedBundle`). Ship new `server/`/`panel/` files without a bump and every installed instance keeps running the old copy (the home server's Ramble after phase 1, 2026-09-07). A node-server bundle must also declare its bare imports in its own `package.json` (guarded by `tests/bundle-server-deps.test.js`) or the installed copy cannot resolve them. The compose file is the exception: `catchUpInstalledCompose` catches it up on EVERY boot at any version (never over an owner edit, never when a required `${X:?…}` is unset), so compose edits — project name, volume/service renames — reach every install without a bump.

## Public repository hygiene

This repository is **public**. Process documents (design specs, implementation plans, session handoffs, ledgers, incident write-ups) live in the private engineering repo (`~/crow-engineering`, a clone of the private Gitea repo: `specs/`, `plans/`, `handoffs/`, `runbooks/`), never here. Code comments refer to them as "the private engineering notes", without paths.

- Never write personal names, real hostnames or tailnet names, real IP addresses, or credentials into tracked files, commit messages, or PR text. Use placeholders: `crow.example.ts.net` / `<tailnet-host>`, `100.64.20.x`, neutral names ("alex", "second user").
- The guard is `scripts/check-public-hygiene.mjs` (CI `static-checks` + `tests/public-hygiene.test.js`). It refuses process-doc paths (`docs/superpowers/`, `.superpowers/`, `handoffs/`, `*handoff*` docs, `.claude/`), literals piped into `sudo -S`, sshpass with an inline password, real-looking `*.ts.net` hosts, and common secret patterns. Placeholders and known-fake test values go in `scripts/public-hygiene-allowlist.txt`.
- Locally it also applies an untracked personal-token denylist, `~/.crow-public-denylist` (one token per line — a substring match — mode 600; CI skips it). A `host: <name>` line there is different: it names a private host and is flagged only in a host-*shaped* use (`ssh [user@]<name>`, `user@<name>`, a dotted `<name>.<tld>`, `<name>:<port>`, or a `//<name>` URL authority). A bare word never matches — private host names are ordinary words the product itself uses (a game's bird species) and appear inside identifiers that must stay — and paths are not checked, so file names may contain one. A violation reports only the line index and the shape (`private host name #2 (host-shaped: ssh target)`), never the name. Enable the sample pre-push hook per clone with `git config core.hooksPath scripts/hooks`.

## Network exposure invariant

The Crow's Nest dashboard and all private routes (MCP, AI chat, storage, push, instance sync) **must never** be reachable via Tailscale Funnel. Only `/blog`, `/robots.txt`, `/sitemap.xml`, `/.well-known/`, `/favicon.ico`, and `/manifest.json` are public-safe on the gateway.

One public surface exists outside the gateway: the **artifact public-link listener**. It is a separate minimal process that runs as its own system user, with no database access, no gateway imports and no route to the dashboard or any private route. It reaches the gateway only through one unix socket that systemd owns. Tailscale Funnel exposes it only through the artifacts sidecar's port 8443. It serves only:

- `GET /a/<token>`: an artifact version its owner explicitly published (unchanged from D16; reports never use it);
- `GET /r/<token>`: exactly one report version that a live report delivered to an approved recipient, never a preview;
- `POST /r/<token>/comment`: a comment from that recipient, only when their token carries comment scope. Tokens are 43-character base64url values, stored hashed. The listener shares no code path, middleware or session handling with the gateway, strips incoming cookies, and sends a CSP `sandbox` header on every response.

Enforced in four layers:
1. Server-side middleware in `servers/gateway/index.js` rejects any request carrying `Tailscale-Funnel-Request` unless the path matches `PUBLIC_FUNNEL_PREFIXES` or `CROW_DASHBOARD_PUBLIC=true`.
2. `isAllowedNetwork()` in `servers/gateway/dashboard/auth.js`.
3. Funnel config: never map `/`; use `tailscale funnel --set-path=/blog`. The public-link listener is the only mapping on Funnel port 8443.
4. The public-link listener routes only `^/a/[A-Za-z0-9_-]{43}(/[^?#]*)?$`, `^/r/[A-Za-z0-9_-]{43}$` and `POST ^/r/[A-Za-z0-9_-]{43}/comment$`, and returns a sandboxed 404 for everything else; the artifact origin returns 403 to any request carrying `Tailscale-Funnel-Request`.

If you touch any of these, run `tests/auth-network.test.js`.

Unrelated to Funnel, but easy to confuse with it: the installer's Caddy reaches the gateway over a dedicated unix socket that **systemd** owns — the `crow-gateway-proxy.socket` unit listens on `/run/crow-proxy/gateway.sock` as `root:caddy` mode `0660`, and `crow-gateway.service` takes the listening fd by socket activation (`Sockets=`/`Requires=`/`After=crow-gateway-proxy.socket`, read in `servers/gateway/proxy-socket.js` via `LISTEN_PID`/`LISTEN_FDS`/`LISTEN_FDNAMES`). The gateway therefore never creates, chmods or unlinks a socket path, and no user is added to the operator's group: only Caddy can open it, so a bot running as the gateway's own user cannot forge a `proxy` peer. Its visitors classify as a verified `proxy` with the client Caddy named (the rightmost `X-Forwarded-For` hop only). `CROW_TRUSTED_PROXIES=loopback` is **not** an acceptable fix for an owner locked out behind Caddy (see `loopbackProxyWarning` in `servers/shared/peer-class.js`); existing installs get a Fix-it card pointing at `scripts/fix-caddy-proxy-socket.sh`, which installs the unit, restarts both services and fails (restoring everything) unless `https://<site>/health` answers 200 through Caddy.

- **WebSocket upgrades**: every `server.on("upgrade")` handler claims its own path SYNCHRONOUSLY (before its first `await`), with `claimUpgrade(req)` from `servers/shared/ws-upgrade-claim.js` — from an installed bundle's own copy, by setting `req.crowWsClaimed = true` (documented in `docs/developers/creating-panels.md` and `docs/developers/bundles.md`). The gateway's fallback answers an upgrade NOBODY claimed with `404 Not Found` and closes the socket, so a new handler that forgets the claim looks like a 404 rather than a hang — but it only writes into a socket NOBODY answered (`upgradeSocketUntouched`): a socket that already carries bytes, or a queued write, is left alone, so a handler that completes a `101` synchronously without claiming (an installed copy from before the contract, a third-party panel hook) keeps its connection instead of collecting a 404 inside the WebSocket stream.
- **Relayed sockets never authenticate as the owner.** Every mount's OAuth fallback passes through ONE bearer middleware, `createBearerAuthMiddleware` in `servers/gateway/bearer-auth.js` (built once in `index.js`, handed to `mountMcpServer`, `/crow.md`, the dashboard token routes), and it refuses a socket carrying the egress relay's mark (`isRelayedSocket`, `servers/shared/bot-doors.js`) with the same `401`/`WWW-Authenticate` challenge an unknown token gets — never running the verifier. `dashboardAuth`, `sessionFromRequest` and `loginNetworkAllowed` refuse the mark the same way (`dashboard/auth.js`). A contained bot has `crow.db` bound read-write, so it can mint its own `oauth_tokens` row; only the path-scoped door tokens (board, phone, artifacts, secrets, sharing-bot, reports, mail-draft, peer-relay, the `llm` doors) plus their signed actor signatures admit a relayed caller. The SAME rule applies to every other credential whose verifier lives in bot-writable `crow.db`, one `isRelayedSocket` check per verifier: the full local token and the models token on the model door (`routes/llm-router.js` `doorCallerAllowed`) and on `/llm/models` lifecycle (`routes/llm-models.js`), a paired instance's peer bearer (`instanceAuthMiddleware`, `crow_instances.auth_token_hash`; `shared/cross-host-auth.js`), the loopback tool mounts (`loopback-gate.js`, `services`/`satellite-tools`), first-run setup (`dashboard/setup-token.js`), the admin backup endpoint (`routes/admin-backup.js`), the kiosk announce token and a display's device token (`bundles/kiosk/server/runtime.js`), and a glasses device token (`bundles/meta-glasses/panel/routes.js`, `servers/shared/device-store.js` rows). A relayed caller keeps the door it legitimately has: the model door's source rule (no bearer needed) and the cloud door's own token. `tests/oauth-refused-on-relay.test.js` and `tests/relayed-owner-tokens.test.js` pin all of it.
- **A request never makes the gateway fetch itself (confused deputy).** The gateway's request-time forwards read their target from rows a contained bot can write (`providers.base_url`/`api_key`/`gpu_policy`; `crow_instances.gateway_url`), so a target on THIS box would re-enter it on a fresh UNMARKED loopback socket with a bearer the caller chose — bypassing the rule above in one hop. `servers/gateway/models/self-target.js` (`ownTargetOf`/`isAllowedSelfPath`/`isAllowedSelfForward`/`isRebindableHost`/`pinnedTargetOf`) decides "this host, ANY port": loopback, `0.0.0.0`, every own interface address, and names resolved first (never on-link peers), so a co-hosted sibling gateway counts. **The rule is every caller's** — an operator voice turn and a background job (`completeText`: session summary, report commentary, Ramble) read the same bot-writable row — and a target on this host is allowed only for an exact `/v1/<op>` or `/llm/v1/<op>` model call (`chat/completions`, `completions`, `embeddings`, `rerank`) with no query or fragment, judged BEFORE any fetch and BEFORE `acquireFn`. For a relayed caller `/llm/v1/<op>` is limited further to this gateway's OWN listen port(s) (a co-hosted sibling's model door is not the bot's to drive); a host name that does not resolve is refused (fail closed) for EVERY caller — `*.ts.net` and a localhost-shaped name included — in the door, the voice path, `completeText` and the adapter guard, because the fetch's lookup would be the only resolution of it (N1); the voice path also applies the door's local-class/forbidden/query rules, and the peer relay's `gateway_url` must be an IP literal, `localhost` or a tailnet name with no query or fragment. A rebindable DNS name target (voice path and `completeText`, every caller) is resolved ONCE and the socket is PINNED to that address (`pinnedTargetOf`/`pinnedLookup` through `safeRequest`), so a public cloud host keeps its `Authorization` while a name that answers with this host is refused; **the address that was judged is the address that is dialled**: an OWN-HOST name (`localhost` is 127.0.0.1 AND ::1, a tailnet name this box answers on) is resolved once too, `pinnedTargetOf` reports EVERY answer in resolver order (`dialAnswers`), the own-host vouch (`isKnownLocalModelTarget`) judges them IN ORDER and returns the first it accepted as `address` (refusing only when none passes — so a dual-stack `localhost` whose ::1 has nothing listening still reaches the Ollama/speech server bound to 127.0.0.1), and the connect goes to THAT literal (`dialAt`) — the door, the voice path, `completeText` and every adapter alike — so no second resolution happens between the judgement and the connect and exactly one, judged address is dialled (`tests/local-model-allowlist.test.js`); a provider `api_key` is never attached to a forward that lands on this box, and no forward ever follows a redirect. **A FORBIDDEN ADDRESS is every caller's refusal too**: link-local (`169.254/16`, cloud metadata, `fe80::/10`) and the named metadata hosts are judged on the address itself (`isForbiddenTarget`, `models/door-resolve.js` → `isForbiddenSelfTarget`), literal or resolved — an IP-literal `http://169.254.169.254/v1` used to be called "not this host" and dialled — and an IPv4 EMBEDDED in an IPv6 address decides too (`classifyIp`'s embedded address: NAT64 `[64:ff9b::a9fe:a9fe]`, SIIT, 6to4, Teredo). the bundle's `OLLAMA_HOST` is a full URL, not a port option), so EVERY other own-host port — 80/443 behind a local Caddy, a gateway's 3001/3008, 3009, 8080, any port a bot chose — is refused for that kind), with every credential header dropped (`Authorization`, `x-api-key`, `api-key`, `x-goog-api-key`, `Ocp-Apim-Subscription-Key`, `xi-api-key`); a rebindable name resolved once and pinned (`pinnedLookup` through `safeRequest`, SSE still streamed), an own-host NAME resolved once and dialled at the literal the vouch accepted, no redirect ever followed; ## Bot Builder (pi-bots)

`scripts/pi-bots/` runs Gmail-driven bots through `@earendil-works/pi-coding-agent`. Bridge spawns pi per-turn (`--mode rpc`), reads inbound mail, drives pi, sends pi's reply text back. Per-turn timeouts from env (`PIBOT_PROMPT_ACK_TIMEOUT_MS`, `PIBOT_TURN_TIMEOUT_MS`) — local-model deployments tune these via systemd drop-in. Pi is spawned `detached:true` so `close()` can SIGTERM its whole process group (otherwise MCP children leak). Concurrency + age + RSS reaper in `pi_lifecycle.mjs`.

Channels: Gmail (`bridge_tick.mjs`) and Discord (`discord_gateway.mjs`) route through the pi bridge. **Meta Glasses** and the **Kiosk display** are voice channels that run their own loop (not pi) in `servers/gateway/voice/turn.js`; voice itself answers as `crow.voice` (next paragraph). Voice turns route models via the gateway's in-process `/llm/v1` router (`servers/gateway/routes/llm-router.js`): fast `crow-voice/qwen3.5-4b` (`:8011`, text-only) → escalate to `crow-chat/qwen3.6-35b-a3b` on a leading `!escalate` (or tool intent). Voice model resolution is DB-`providers`-first via `servers/gateway/ai/resolve-profile.js`. See `docs/guide/kiosk-mode.md` + `docs/architecture/kiosk.md`.

The **AI Companion** (Open-LLM-VTuber + Live2D, `bundles/companion/`, proxied at `/companion`) was retired: its bundle, proxy, kiosk device pairing and settings are gone, and nothing mounts under `/companion` (the gateway answers 404). Device-bound voice is the Kiosk display (`device_kind: "kiosk"`). `device_kind: "companion"` stays readable as a legacy kind for surviving device records but is never created; `companion_features` is readable and no longer written. Any install that still has the bundle installed gets a boot-time Fix-it card (`servers/gateway/fix-it/detectors/retired-bundle.js`) whose one-click Remove runs the product's normal uninstall, driven by the code-held stub in `servers/gateway/retired-bundles.js` (the repo manifest is gone).

Voice (kiosk, glasses, phone) always answers as the Crow voice bot, `crow.voice`; there are no per-device pickers. Crow hands bigger jobs to a bot only after a yes (`servers/gateway/voice/handoff*.js`): a hand-off is a card on the bot's home project made through `board/give-service.js`, logged in `voice_handoffs` (local-only, migration 0018, never synced). A phone, glasses or dashboard tab confirms by voice; on a kiosk (a shared display) the yes is taken on the phone (`/dashboard/voice/handoffs/:id`). Completion goes through `board/result-requesters.js`. **Relay contract:** any turn run for a non-operator transcript must set `relayThreadId` on `runVoiceTurn` (`relayKind` `"operator"` or `"answer"`), or the text could be taken as the operator's own words (a bot's answer could confirm a hand-off). Allowed targets: `handoff.enabled` / `handoff.allowed_bots` in Crow's voice settings.

Card verbs are gateway-served: the board MCP server mounts at `/board/mcp` (local MCP token, or the path-scoped board token minted at boot to `$CROW_HOME/board-token`). `board_plans`/`board_results`/`board_mutations` live in the instance-global tasks.db ONLY (never per-project stores). The dispatch prompt reads plan records; bots report outcomes via `board_report_result` (autonomy: `gated` default; `auto` cards self-close on def-terminal `done`). Cards archive (never delete): `archived_at`, Monday-sync pull-only on archived rows.

**A bot definition is MAC'd (tamper-evident authority).** `pi_bot_defs` decides a bot's policy (`tools.crow_mcp`, `permission_policy`, `write_paths`, `project_id`, remote servers) and crow.db is bound read-write into every contained bot, so each row carries `def_mac` (a keyed MAC over the WHOLE canonical definition + `bot_id`/`enabled`/`project_id`/`def_generation`, under `<CROW_HOME>/secrets/token-hmac.key`) and `def_generation` (a replay counter kept OUTSIDE crow.db in `<CROW_HOME>/secrets/bot-def-generations.json`). `macBotDef`/`verifyBotDef` live in `servers/shared/bot-def-mac.js` (HOST-ONLY; the family is `bot:def` in `servers/shared/token-mac.js`), the pre-listen converter in `servers/gateway/boot/bot-def-mac.js` seals existing rows once and marks the era (`token_hmac_era:bot:def`), and `bridge.mjs` `loadBot` refuses an unverified definition (one `[bot-def] … could not be verified (<reason>)` line per bot per 24 h, no spawn). **ONE writer**: `servers/shared/bot-def-store.js` (`writeBotDef`/`setBotEnabled`/`signBotDef`), reached from bot-loadable code (bundles' `server/`, `scripts/pi-bots/**`) through the import-free seam `servers/shared/bot-def-seal.js` — a raw `UPDATE pi_bot_defs` leaves a stale MAC and a bot that cannot run; `tests/bot-def-single-writer.test.js` fails on one. Pre-era rows (no MAC) are accepted; after the era a missing/mismatched MAC, a row that carries no `def_mac` COLUMN at all (`no-mac-column`: the ERA decides, never the row's shape), a column whose type is not the one the writer stores, or stored text that is not the canonical serialization of its parsed value (`definition-text`: duplicate JSON keys have no second reading) is refused. **No write signs content it could not verify**: `writeBotDef` verifies the row it is about to re-sign and refuses an unverified one with `BOT_DEF_UNVERIFIED` (nothing written, no generation bumped, one `[bot-def]` line naming the re-approve command) — only a full-form owner save (the wizard, the voice-bot editor's clean-base branch, the CLI import) may pass `ownerFullReplace` and replace it. **The statement lands only on the row it verified, and every partial write states the row it read**: its WHERE pins `definition`/`enabled`/`project_id`/`def_mac`/`def_generation`, a retry (L2) pins what the previous attempt wrote, and `expectDefinition`/`expectEnabled`/`expectProjectId` are REQUIRED for every update — a caller whose own read differs from the verified row is refused with `caller-read-differs`, and an update that omits any of the three throws `BOT_DEF_EXPECT_REQUIRED` (a programming error; only an insert-only create and a full-form `ownerFullReplace` are exempt). There is no `transform` mode: a derived writer (the artifacts companion migration, the init-pi-bots backfill) reads the row, builds its change from what it read, and passes those values, so a tampered row is refused and skipped. Every successful sealed write (and the converter's TOFU seal, the reapprove CLI and the key-reset reseal) also drops the APPROVED COPY of what it stored in `<CROW_HOME>/secrets/bot-def-approved/<bot_id>.json` (0700 dir, 0600 file; a bot id outside `[A-Za-z0-9._@:-]+` is refused; the copy is removed with the bot), which is what `--show` diffs the stored row against — field by field with the authority keys flagged `!!` and credential-named values in `spawn_env`/`gateways` redacted (`no previous approved version` when there is none); losing the copy only weakens that diff. A History restore verifies the VERSION's own captured `(def_mac, def_generation)` before it re-signs anything. `node scripts/token-hmac.mjs --reset` re-seals every row under the new key (replay floor ON, a row that moved is skipped and listed) — a reset never blesses an unverified row (those are listed and left refused) — and the way back for any refused bot is `node scripts/cli/bot-def-reapprove.mjs <bot_id> --show` then `--approve <digest>` (it re-seals exactly the content the operator read; every bot-written string it prints — keys included — goes through `safeText`, so an ESC/C1/bidi character shows as a visible `\uXXXX`, `--show` warns when the row holds one, and `--approve` then needs `--allow-control-chars`); restart the bridge process(es) after a reset.

**Shared Storage over the fd pipe (bots never read the identity, and never hold the instance key).** A storage-using MCP child — core `crow-storage` (`needs` in `scripts/server-registry.js`) and a bundle whose manifest says `"needs": ["shared-storage"]` **only when its id is also on the reviewed, code-held allow-list** (`isStorageEnvConsumer` / `STORAGE_ENV_CONSUMERS` in `servers/gateway/addon-env.js`: studio, sunvox-studio, data-dashboard, artifacts) — is hydrated from **the bot's OWN storage key**, `<CROW_HOME>/secrets/bot-storage.json`, provisioned by `scripts/ops/minio-bot-storage.sh` (`apply` makes the per-instance `<prefix>-bot-<tag>-policy` policy + `<prefix>-bot-<tag>` MinIO user, tag = first 12 hex of sha256("<hostname>:<realpath of the crow home>"), limited to `projects/*`, `bots/*`, `studio/*`, `sunvox-studio/*` of `<prefix>-files`). `scripts/pi-bots/mcp_writer.mjs` reads it through `servers/shared/bot-storage-key.js` (a `secrets` directory that is a real directory, this user's, exactly 0700; then a regular file opened `O_NOFOLLOW` and fstat'ed on that fd — this user's, no group/other bits, size-capped) and sets only `S3_ENDPOINT`/`S3_USE_SSL`/`S3_REGION`/`S3_BUCKET_PREFIX`/`S3_ACCESS_KEY`/`S3_SECRET_KEY` + `CROW_STORAGE_FROM_HOST=1` in the in-memory block. **No bot block opens `storage.shared.*` any more, in any mode** — that is the instance-wide (root-level) credential, and a sibling sandbox process can read a child's `/proc/<pid>/environ`; the key file lives outside `crow.db` because `crow.db` is bot-writable and a sealed value there is not bound to its setting name. **Two rules keep "only the six S3_* names" true:** (a) before the marker or the hydration, EVERY bot block of every kind loses every storage credential name — all `MINIO_*` and the six `S3_*` names — in BOTH modes (`withoutStorageCredentials`), so the repo `.env`'s MinIO ROOT credential (which the core registry's `mcpEnv` template resolves) can never board a bot config; a bot's only storage credentials are the scoped bot key piped for that turn. **A manifest `needs` is a request, not a grant:** the installed manifest is operator-writable and a store add-on is not reviewed code, so a bundle that declares the need and is not on that list gets storage OFF (marker `0`, no credentials) plus one warning naming it as "not a reviewed storage consumer" (`sharedStorageUnreviewed` out of `crow-server-catalog.mjs`; the core `crow-storage` grant still comes from the registry, which is code in this repo). (b) There is **no env fallback for a bot**: no key file is storage OFF with `shared storage: off (no bot storage key on this instance)`, and a key file that cannot be used (group/world readable, a symlink, oversized, not JSON, a missing field) is OFF with the distinct `shared storage: off (the bot storage key file could not be read: <reason>)` — a fault, not a normal state. Every OTHER active bot stdio block gets the marker `0`: a bundle that imports `s3-client` without declaring `needs` (or an installed copy from before its declaration) still never takes the owner/identity path, and marker-less is reserved for an owner's own spawn. The child calls `adoptHostStorage()` from `servers/storage/s3-client.js` (and `useDbStorageConfigFromInstance` reads the marker itself) and never touches `identity.js`; in a hydrated child availability is a non-recursive one-key `listObjectsV2` under `bots/` (**never `bucketExists`/HeadBucket — MinIO reads it as `s3:ListBucket` with no prefix, so the policy's `s3:prefix` condition refuses it — never `listBuckets`, never `makeBucket`**, which is a no-op: the operator provisions the bucket), `getBucketStats` sums only the four granted prefixes (the empty prefix of a whole-bucket listing is refused), and an S3 AccessDenied reports `storage refused this location`; a **file-delivery** turn carries no credentials, so the child gets `CROW_STORAGE_FROM_HOST=0` (no shared storage at all, one warning — never a silent localhost:9000 fallback), and the spawn log says `shared storage: over fd` / `off (file delivery)`. A bot's project-less `crow_upload_file` writes under `bots/<bot_id>/` (its key may not touch the bucket root), and a `storage_files` row records the bucket actually written (`<prefix>-files`, not a hardcoded `crow-files`).
